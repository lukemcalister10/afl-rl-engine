ENVIRONMENTAL NOTE -- THREAD OVERSUBSCRIPTION, AND THE FIX
---------------------------------------------------------
The first attempt at the on2/on3 rebuild and at the identity gate had to be abandoned: both processes
accrued hours of CPU without finishing. The cause is environmental, not a fault in the engine or in
this order's code, and it is recorded here because determinism is exactly what it threatens.

The panel environment (run_panel.sh, and every harness that copies it) pins ONLY
OPENBLAS_NUM_THREADS=1. The other BLAS/threading pools -- OMP, MKL, NUMEXPR, VECLIB -- are left
unpinned, so each engine process spawns worker threads that SPIN-WAIT. One such process is merely
wasteful; TWO of them on this 4-core box starve each other indefinitely (measured: load average 8.5
with two runnable processes, ~2 CPU-minutes burned per wall-minute, no completion).

THE FIX, applied to every run recorded above and to the gate:
    export OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 \
           NUMEXPR_NUM_THREADS=1 VECLIB_MAXIMUM_THREADS=1
and run engine processes SEQUENTIALLY, never two at once.

Effect, measured on this box: the identity gate went from 1h53m of CPU without finishing to
COMPLETING IN ABOUT FOUR MINUTES. The determinism rebuild likewise.

WHY IT DOES NOT TAINT THE RESULT: every md5 in the table above comes from a run that COMPLETED. A
starved run produces no board at all -- it does not produce a wrong one -- so the failure mode is a
hang, never a silent divergence. The partial workspaces from the abandoned attempts were deleted and
the runs redone from scratch. The determinism PASS above is on two clean, completed, fully-pinned
builds.

CARRIED FORWARD: the pinning belongs in the panel/bake environment itself, not in each harness that
remembers to add it. Named as a hygiene item for the landing act, not fixed here (this order does not
touch run_panel.sh).
