#### DOES IT MOVE THE BOARD IDENTITY? — **YES, and the proof is direct.**

The board identity **is** the md5 of that file. Measured:

```
$ md5sum data/rl_build/rl_app_data.json
68be10c79d0ee096455754e084bcf757

$ cat data/rl_build/rl_app_data.json.srcmd5
{"derived":"rl_app_data.json","own_md5":"68be10c79d0ee096455754e084bcf757", …}
```

and `68be10c7` is the live board id of record in `data/expected_boot.json`,
`data/release_contract.json`, `data/release_lineage.json`, `data/book_stable_seal.json`, both UI
bundles, `ui/data/movers.js`, and the three history files. `ui/tools/extract_board_view.py`'s own header
states the ring-fence: *"md5(rl_app_data.json) == the pinned board id"*, and the app fail-closes when
`stamp.srcmd5` disagrees with the expected board.

So **adding one integer field to 804 + 198 rows changes the file bytes, changes the md5, and therefore
retires board `68be10c7` and mints a new board id.** Under `tools/landing/carriers.py`, that is a full
**LEVER-CLASS LANDING**: 19 declared carriers move together —

| group | carriers |
|---|---|
| identity manifests | `data/expected_boot.json` · `data/release_contract.json` · `data/release_lineage.json` |
| board + sidecars | `data/rl_build/rl_app_data.json` (+`.srcmd5`) · `engine/rl_after/rl_app_data.json` (+`.srcmd5`) |
| store | `engine/rl_after/rl_model_data.json` (must be proven **byte-unmoved**) |
| histories | `value_history.json` · `rank_history.json` · `pos_rank_history.json` (a new out-of-round column) |
| UI bundles | `board_view_working.js` (BOTH writers) · `board_view_public.js` · `movers.js` · `movers_transition.js` |
| sibling repin | `sibling_repin_state.json` · the FV oracle + fixtures keyed to the board id · the `.sibling_txn` dir |

plus a lineage entry, a `release_contract` restamp, a `sibling_repin` reconcile (the balanced board
moves), `release_manifest_check` GREEN, `acceptance.runner` GREEN, and — because a landed change owes one
— **an out-of-round column and a label the owner must set** (see item 16: *"A COLUMN IS WRITTEN ONCE PER
LANDED CHANGE"*, *"do not ask for a label mid-job"*). It would also be the first landing to add a **new

values that must not move.

The saving grace: it is a **display-only, zero-EV** change of exactly the class the record already blesses
— `rl_export.py:361` says of the attribution sidecar, *"DISPLAY-ONLY: neither field feeds `v` (every board
value is the already-computed engine ev; zero EV movers)."* Every value would be provably unmoved; only
the identity moves.

#### THE TWO ROUTES, EVALUATED

**ROUTE A — the field rides the board (`rl_export.py` → `rl_app_data.json`).**
- Precedent: exact. `vPrev` and `levers` are display-only, per-key, sidecar-sourced, and live in the row.
- Cost: the full landing above. Board id retires, ~19 carriers move, new lineage entry, an owner-set
  column label, all gates re-run, `~13 min` of builds before any acceptance stage even starts (the
  register's measured floor), and the P2a lander's own no-op dry run is machine-timed at **563.5 s**.
- Benefit: v0 becomes part of the board of record, versioned with it, impossible to go stale, and
  visible to every consumer including future evidence instruments.
- Risk: adds a *field-schema* precedent to a file whose bytes are the system's identity. Every future
  "just one more column" is then also a landing.

**ROUTE B — a derived UI sidecar (`ui/data/v0.js`), board untouched.**
- Precedent: also exact, and closer to the request. `ui/data/ownership.js`, `ui/data/club_valuation.js`,
  `ui/data/movers.js` and `ui/app/positions_data.js` are all generated `window.__…__ = {…}` bundles that
  the app loads beside the board. The board id does not move; **no landing, no lineage entry, no column,
  no owner label.**
- The governing law it must obey, `ui/app/ownership.js:25`: *"A mirror that does not name the identity it
  was generated from is not a mirror."* So `ui/data/v0.js` must be stamped with the board md5 + store md5
  it was generated from, and `MD.v0` must **refuse** (render nothing, report the row) when the stamp
  disagrees with the loaded board — the same fail-closed shape `ownership.js` already implements.
- The one real constraint: **`ui/tools/` cannot compute v0.** Every tool there trims and joins; `v0_start`
  needs the engine loaded with its pinned artifacts. So the generator is a new script that imports the
  engine read-only, iterates the roster, calls `v0_start(p)`, and writes the bundle — precisely the shape
  of the day-0 evidence scripts (`docs/evidence/staircase_fix_2026-08-20/sfx_day0.py` and siblings) which
  already load the engine, assert the live board md5, and write a keyed JSON, read-only throughout.
- **And v0 is nearly static, which is what makes Route B safe.** `_ageR(p)` at `:2154` is age as of the
  *draft year*, and `_v0key`'s value depends only on `(future position, draft age, pick)` off a **frozen**
  surface. v0 does not move on a round advance. It moves only when (i) the store changes a player's
  dob / pick / type / future position, (ii) the v0 surface or ruled curve is re-cut (bake-class), or
  (iii) the roster changes. So the sidecar regenerates on store moves and bakes, not weekly.
- Cost: the new generator must join the release manifest as a checked carrier (the v785 owner ask — *"one
  manifest enumerating the entire shipped set … refuses to finish while anything is stale"*), and P2a's
  lander needs one more step. That is bounded and is exactly what the lander exists for.

#### RECOMMENDATION: **ROUTE B, the stamped sidecar.**

Three reasons, in the order I'd give them to the owner:
1. **It is not board data.** v0 is a draft-time property off a frozen surface, not a priced position on
   this week's board. Putting a static draft-time constant inside the artifact whose md5 *is* the live
   board's identity is a category error that costs a landing every time it is touched.
2. **The cost asymmetry is enormous.** Route A: a full 19-carrier landing, a retired board id, an
   owner-set column label, every gate re-proved — to show a number that does not change. Route B: a
   generator, a stamped bundle, a reader, a test.
3. **The record's own doctrine points here.** `ui/app/ownership.js` states the sidecar law and its one
   red line — *"POSITIONS ARE NOT HERE. They feed valuation … If positions ever appear in this file, the
   live lane has become an engine trigger and the whole design is undone."* v0 does **not** feed
   valuation on the display path; it is already-computed, display-only, zero-EV — the same category as
   `vPrev` and `levers`. It is on the right side of that line.

**The one condition on the recommendation:** if the owner wants v0 to be part of the *published* record —
quotable in evidence, versioned with the board, readable by future instruments — then Route A is correct
and the landing is the honest price. Put that question to him in one sentence; do not decide it in a seat.

**Cheap hedge if he is unsure:** build Route B now (it is reversible and touches nothing pinned), and if
v0 later earns a place in the board of record, fold the field into the *next* landing that is happening
anyway — a lever landing or the R24 advance — where the carriers are moving regardless and the marginal
cost is one line in `player_rec()`.

### (b) RANKING — where does v0-rank come from?

**Rank-now already exists and is computed in the browser.** `ui/app/board.js:99`:

```js
pool.sort(function (a, b) { return b.val - a.val; });
pool.forEach(function (r, i) { r.rank = i + 1; });
```

So the board's rank is not stored — it is derived on every render from the value-descending sort of the
visible pool (with pick-assets excluded at lens ≤ 2 by owner ruling). **v0-rank is therefore free once v0
per row exists: it is the same three lines sorting on `v0` instead of `val`.** No engine work, no new
history file, no export change.

`engine/rl_after/ingestion/rank_history.json` is a *different* object and is **not** a v0 source: it
carries rounds 14–23 plus the registered out-of-round columns, i.e. the weekly rank trace. Its earliest
point is R14, long after entry. Do not try to derive v0-rank from it.

#### THE HONEST PROBLEM WITH v0-RANK — measure it before promising it

`docs/ENGINE_PRIMER.md:170` states it plainly:

> "**`v0` in a matrix row** = the surface's slot value — **identical for every same-(pos, age, pick)
> player.** It is a MODEL BELIEF, not that player's outcome."

I measured the tie structure on today's 804 active rows (draft age approximated as `age − (2026 − yr)`,
so treat as close, not exact):

| measure | value |
|---|---|
| active rows | 804 |
| distinct v0 slots | **453** |
| rows sharing a slot with ≥1 other player | **527 (66%)** |
| largest single slot | **14 players** (SF, draft age 18, no pick) |
| next largest | 11 (SD/18/none) · 10 (MID/18/pk 7) · 9 (MID/18/pk 2) · 9 (MID/18/pk 5) |

**Two thirds of the board would be tied.** A naive `rank(v0)` produces blocks of up to 14 players at one
rank, and "rank change vs v0" for a player inside a 14-block is an artifact of the tie-break, not a fact
about him. This needs an owner ruling before it is built — the options, symmetrically:
- **(i)** dense rank with the tie count shown ("v0 rank 27= of 14 tied") — honest, ugly, no invented order;
- **(ii)** rank the v0 *slot*, not the player, and show "entry band" rather than "entry rank";
- **(iii)** a declared tie-break (e.g. by pick, then name) — clean-looking, and it manufactures order the
  model does not have. The register's standing posture would reject this on sight ("displaying false
  information", the A19 precedent).

My lean: **(ii) or (i)**. The *absolute* and *relative value* change vs v0 has none of this problem and is
the stronger half of the owner's ask.

#### THE SECOND CAVEAT — pool entrants
114 of 804 active rows carry no pick or a pool pick (`ty` breakdown: ND 589 · RD 66 · MSD 63 · SSP 28 ·
PDN 16 · PDA 15 · IRE 14 · UNR 13). For pool entrants the record is explicit that `v0_start` is **not**
their entry price any more — `_merged_recover.py:2652`, the owner's addendum 6: *"for a pool entrant the
pool-slot-derived `v0_start` no longer sets his entry price, even where the signed level cuts"*; their
anchor is the #326 signed per-division level (ladder currency × 1.0524 into engine units). And
`ENGINE_PRIMER.md:124` records that the walk-forward book's `v0` field for POOL rows *"still carries the
SUPERSEDED old-surface belief (cleanup queued)"*.

So a v0 column must either (a) source pool rows from the #326 signed entry anchors, or (b) declare them
`slots.ABSENT` and render an explicit "no v0 anchor — pool entrant" — never a dash, per the templates'
law. Shipping `v0_start` for those 114 rows would put a superseded number on the owner's screen.

### (c) UI — which surfaces, and is the board view templated?

**Is the board view templated? No.** `ui/templates/` covers five standalone report pages (tracker,
players, year1, noarb, movers). The board view is `ui/app/board.js` building `innerHTML` strings; there
is no skeleton, no slot manifest, and no `slots.render()` caller anywhere outside the self-test. So this
feature does **not** get the templates' "missing value is a loud failure" protection for free — it must
implement that discipline by hand (see item 4).

**Surfaces, in the order I'd build them:**

1. **Player card (`ui/app/card.js`) — build here first.** It already has the per-player statrow, the
   rank-with-denominator ("136 of 804"), the lens chart and the (empty) waterfall. A four-figure block —
   **v0 · now · Δ abs · Δ %** plus **entry rank → rank now** — lands with no layout fight and is where a
   single player's story belongs. It is also where the tie caveat is cheapest to state honestly, in words,
   once. Both tiers: the working card and `renderPublic()`. Note the existing public/working ruling —
   `vRaw`, the override line and the attribution panel are deliberately withheld from public; v0 is a
   model belief about a draft slot, so it is arguably public-safe, but **that is the owner's tier call,
   not a seat's** (the two-tier law is explicit that the public bundle is leak-proof *by construction*).

2. **Board view (`ui/app/board.js`) — columns, behind a toggle.** Adding four columns to a row that the
   UI review already found overcrowded (mobile drops the wrong columns; the grid was rebuilt once to stop
   a seventh cell wrapping under the name at `:345`) is the risk. Ship them as a **sortable column group
   the owner switches on**, not as default row furniture — and note this collides pleasantly with UI-review
   Phase 3 (search / sort / sticky), which is exactly the machinery a v0-sortable column wants. If it
   lands as a default column it should displace the dead `Δ VS ROUND` columns (item 8), not sit beside
   them.

3. **Movers page — leave alone.** Movers is a *between two points* surface; v0 is an *all-time anchor*.
   Mixing them re-opens the boundary-semantics question the from/to redesign closed at v510.

4. **`ui/templates/players.html`** — if the owner wants v0 in the printed players document, that is 4 more
   slots and a manifest entry (both-direction cross-checked, so the markup and the manifest move together).
